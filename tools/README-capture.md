# Проверить сохранённый CSV, не подменяя аппаратный опыт

`check_capture.py` работает с уже сохранённым текстовым файлом. Нужен Python 3.10 или новее; сторонних пакетов нет. Скрипт не открывает serial-порт, не прошивает плату и не может определить, откуда на самом деле взялись числа.

Из корня репозитория:

```sh
python3 tools/check_capture.py evidence/run.csv
python3 tools/check_capture.py evidence/normal-run.csv --require-no-loss
python3 -m unittest discover -s tests -p 'test_capture_checker.py' -v
```

На Windows, если Python установлен с launcher, замени `python3` на `py -3`. В PowerShell используемые команды Python не требуют Bash. Пути к файлам с пробелами заключай в кавычки.

Exit codes:

- `0`: формат, диапазоны и переходы сессий прошли заданные проверки
- `1`: неверный/пустой/незавершённый файл, неправильные значения/последовательность или потери при `--require-no-loss`
- `2`: файл не удалось прочитать либо неверны аргументы CLI

Без `--require-no-loss` намеренно перегруженный, но правильно сформированный лог может пройти: gaps и счётчики показываются отдельно. Нельзя складывать sequence gaps и reported drops как независимые потери — они могут описывать одни и те же записи.

## Точный контракт

```text
seq,t_ms,n,min,max,mean_x100,freq_mHz,signal_valid,dropped_adc,dropped_tx
```

Все поля — десятичные uint32_t. `n=100` по умолчанию; для осознанно изменённого эксперимента есть `--expected-n 50`. ADC-коды 0…4095, среднее ×100 между min/max. `signal_valid` относится к измерению частоты: для 0 требуется `freq_mHz=0`; для 1 — ненулевая частота. Отдельный ADC deadline fault означает остановку нормального потока, а не смену этого бита.

Файл может содержать CRLF или LF; последняя строка тоже должна завершаться LF. Отсутствие финального newline считается возможным обрывом. NUL, bare CR и управляющие/Unicode-разделители вместо LF не принимаются как границы записей. Header точный, вокруг числовых полей нет пробелов. Если capture начался посередине кадра, сохрани оригинал и отдельно создай обрезанную копию с документированным диапазоном полных записей; не выдавай её за непрерывный исходный лог.

В начале и после каждого reset/START передавай сначала CRLF, затем блок ниже. Начальный CRLF не даёт старой строке, оборванной reset, склеиться с новым `# session=...`:

```text
# session=boot-or-start-id
# clock=HSI8_nominal
# vdda_mV=unknown
seq,t_ms,n,min,max,mean_x100,freq_mHz,signal_valid,dropped_adc,dropped_tx
```

Это образец метаданных, не аппаратный лог. Конкретный ID выбери так, чтобы различать сессии в своём эксперименте.

- Только строка `# session=...` и повторный точный CSV header задают новую сессию
- После `# session=...` нужен header; затем хотя бы одна data-строка
- Обычные `# status ...`, `# fault ...`, `# build ...` — комментарии, они не обнуляют проверку sequence/drop
- Неизвестный обычный текст, например `OK STATUS`, считается ошибкой формата. Во время capture не вводи команды либо выводи человеческие ответы с `#` через единого владельца TX
- Sequence/time допускают unsigned 32-bit wrap. Разница не менее половины диапазона считается обратным ходом; это соответствует коротким последовательным учебным записям, не произвольному многомесячному разрыву
- Drop-счётчики не уменьшаются внутри сессии; при UINT32_MAX они насыщаются

Скрипт показывает first/last seq и span **по времени MCU**, который не является независимым измерением точности HSI или реальной длительности опыта. Длительный gate дополнительно засекай часами ПК/внешним прибором.

## Проверить достаточность записи для L10

Без дополнительных флагов даже одна корректная data-строка проходит проверку формата. Для нормального минутного опыта используй:

```sh
python3 tools/check_capture.py evidence/normal-run.csv --require-no-loss --min-rows 600 --min-device-span-ms 59000 --expected-period-ms 100 --period-tolerance-ms 5
```

- `--min-rows`: минимум **в каждой сессии**, не сумма после нескольких reset
- `--min-device-span-ms`: минимум между первой и последней data-строкой каждой сессии. 600 строк через 100 мс дают 59 900 мс span; это не 600 интервалов
- `--expected-period-ms`: добровольная проверка интервала меток MCU **на единицу seq**. Для seq 1→4 ожидается 300 мс, даже если две строки потеряны
- `--period-tolerance-ms`: абсолютный допуск на этот интервал, по умолчанию 5 мс. Это учебный порог для меток callback, не допуск HSI. Он применяется только вместе с expected-period

Для L10 сначала включи capture в терминале, затем нажми Reset платы, не отключая USB-UART и логирование. В прошивке metadata и точный header должны быть переданы **до автоматического запуска acquisition**, как описано в L10 §5; не дописывай их в сохранённый файл.

Через не менее 65 с по часам ПК останови только логирование. Плата продолжает acquisition; команды STOP в L10 ещё нет. Сохрани оригинал. Проверяемая копия при необходимости ограничивается интервалом от metadata/header нового boot до последней полной строки с LF: исключи только старый фрагмент до этой сессии и незавершённый хвост без LF. Запиши границы обрезки и первый/последний seq; повреждённые завершённые строки не вырезай. PASS относится к выбранному интервалу, не к опустошению очереди или полноте данных после него.

Только если уже реализован протокол L12, вместо reset используй новый START из IDLE. Если опыт намеренно изменён, сначала пересчитай условия и затем задай параметры; не расширяй допуск только ради PASS. Для перегрузочного файла не требуй no-loss.

Cadence не заменяет внешний измеритель: TIM3 и SysTick получают время от одного HSI. Метки в main вместо callback могут показывать задержку обработки; это другая измеряемая величина. Скрипт проверяет согласованность заявленного договора, а не происхождение метки.

## Что ещё должен сделать человек

Сопоставить CSV с реальным действием на входе; проверить run/build ID, схему, инструменты и происхождение файла. Просмотреть fault/status: произвольные комментарии `# fault ...` не имеют машинного диагноза в этом формате. Checker не видит потерь до первого или после последнего seq. Старые записи могут содержать старый снимок dropped_tx: после перегрузки дождись новой принятой записи с актуальным счётчиком, а затем её передачи. `PASS` означает корректность проверяемого формата и инвариантов, а не доказательство электроники, точного напряжения или независимой частоты дискретизации.

Все данные в `tests/test_capture_checker.py` **синтетические** и проверяют сам checker. Они не являются evidence L10/L12/L13.
