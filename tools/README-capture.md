# Проверить сохранённый CSV, не подменяя аппаратный опыт

`check_capture.py` работает с уже сохранённым текстовым файлом. Нужен Python 3.10 или новее; сторонних пакетов нет. Скрипт не открывает serial-порт, не прошивает плату и не может определить, откуда на самом деле взялись числа.

Из корня репозитория:

```sh
python3 tools/check_capture.py evidence/run.csv
python3 tools/check_capture.py evidence/normal-run.csv --require-no-loss
python3 -m unittest discover -s tests -p 'test_capture_checker.py' -v
```

На Windows, если Python установлен с launcher, замени `python3` на `py -3`. В PowerShell используемые команды Python не требуют Bash. Пути к файлам с пробелами заключай в кавычки.

Exit codes:

- `0`: формат, диапазоны и переходы сессий прошли заданные проверки
- `1`: неверный/пустой/незавершённый файл, неправильные значения/последовательность или потери при `--require-no-loss`
- `2`: файл не удалось прочитать либо неверны аргументы CLI

Без `--require-no-loss` намеренно перегруженный, но правильно сформированный лог может пройти: gaps и счётчики показываются отдельно. Нельзя складывать sequence gaps и reported drops как независимые потери — они могут описывать одни и те же записи.

## Точный контракт

```text
seq,t_ms,n,min,max,mean_x100,freq_mHz,signal_valid,dropped_adc,dropped_tx
```

Все поля — десятичные uint32_t. `n=100` по умолчанию; для осознанно изменённого эксперимента есть `--expected-n 50`. ADC-коды 0…4095, среднее ×100 между min/max. `signal_valid` относится к измерению частоты: для 0 требуется `freq_mHz=0`; для 1 — ненулевая частота. Отдельный ADC deadline fault означает остановку нормального потока, а не смену этого бита.

Файл может содержать CRLF или LF; последняя строка тоже должна завершаться newline. Отсутствие финального newline считается возможным обрывом. NUL запрещён. Если capture начался посередине кадра, сохрани оригинал и отдельно создай обрезанную копию с документированным диапазоном полных записей; не выдавай её за непрерывный исходный лог.

В начале и после каждого reset/START передавай:

```text
# session=boot-or-start-id
# clock=HSI8_nominal
# vdda_mV=unknown
seq,t_ms,n,min,max,mean_x100,freq_mHz,signal_valid,dropped_adc,dropped_tx
```

Это образец метаданных, не аппаратный лог. Конкретный ID выбери так, чтобы различать сессии в своём эксперименте.

- Только строка `# session=...` и повторный точный CSV header задают новую сессию
- После `# session=...` нужен header; затем хотя бы одна data-строка
- Обычные `# status ...`, `# fault ...`, `# build ...` — комментарии, они не обнуляют проверку sequence/drop
- Неизвестный обычный текст, например `OK STATUS`, считается ошибкой формата. Во время capture не вводи команды либо выводи человеческие ответы с `#` через единого владельца TX
- Sequence/time допускают unsigned 32-bit wrap. Разница не менее половины диапазона считается обратным ходом; это соответствует коротким последовательным учебным записям, не произвольному многомесячному разрыву
- Drop-счётчики не уменьшаются внутри сессии; при UINT32_MAX они насыщаются

Скрипт показывает span **по времени MCU**, который не является независимым измерением точности HSI или реальной длительности опыта. Длительный gate дополнительно засекай часами ПК/внешним прибором.

## Что ещё должен сделать человек

Сопоставить изменения CSV с реальным действием на входе; проверить run/build ID; отдельно записать схему и инструменты; проверить, что исходный файл сохранён с платы. `PASS` означает корректность проверяемого формата и инвариантов, а не доказательство электроники, точного напряжения или независимой частоты дискретизации.

Все данные в `tests/test_capture_checker.py` **синтетические** и проверяют сам checker. Они не являются evidence L10/L12/L13.
