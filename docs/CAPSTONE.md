# Итоговый низковольтный регистратор сигналов

Ты собираешь стендовый прибор, который одновременно получает аналоговые отсчёты, измеряет частоту импульсов, принимает команды и сохраняет данные на компьютер. Он развивает полезные для будущего мотор-тестера навыки, но его входы рассчитаны только на учебные сигналы в пределах питания MCU.

**Не подключать к автомобилю, цепям зажигания, двигателю, силовым ключам, сети или неизвестному генератору.** Внешний входной тракт, защита и проверка реальных переходных процессов являются отдельным проектом.

## Что должно получиться

- Один ADC-вход с номинальной частотой 1000 отсчётов/с.
- Один вход частоты для положительных импульсов 0–3,3 В в учебном диапазоне 100–1000 Гц.
- Низковольтный тестовый PWM-выход той же платы.
- Сводка по 100 ADC-отсчётам, то есть номинально 10 записей/с.
- UART-консоль, CSV-файл на компьютере и понятные состояния прибора.
- Ограниченные очереди, видимые потери, ограниченные ожидания и восстановление после зависания.

Это **регистратор сводок**. Он сохраняет минимум, максимум и среднее каждого блока, а не исходную осциллограмму из 1000 отсчётов/с. Короткие выбросы могут попасть в min/max без восстановления их формы. Для записи формы сигнала потребуется другой контракт данных и отдельный расчёт полосы/памяти.

## Задача: прибор можно передать другому человеку

Представь, что завтра нужно оставить этот стенд на столе коллеге. Он должен по твоей инструкции получить данные, заметить пропавший сигнал и восстановиться после предусмотренного отказа. Эта передача определяет объём проекта: понятные пределы и воспроизводимость важнее нового дисплея или ещё одного датчика.

**Фиксируем до реализации:** профиль ниже, формат версии 1 и условия T01–T10. **Выбираешь и обосновываешь сам:** bounded-очереди, документированную политику остатка при STOP и порядок обслуживания метаданных/ответов/CSV одним передатчиком. После выбора обнови соответствующий тест; нельзя незаметно менять правило, чтобы засчитать неудачный прогон.

Первый рабочий срез — реальный ADC-вход и сохранённая сводка. Потом добавляются частота, управление и recovery. На каждом шаге сравни поведение с предыдущим рабочим build; это даёт место поиска причины, если целый прибор перестал работать. План в [L12](labs/12-capstone-integration.md) последовательно убирает опоры, а [L13](labs/13-capstone-validation.md) проверяет самостоятельное изменение.

## Аппаратная конфигурация

Используй [общий pinmap](ROADMAP.md) и правила [SAFETY](SAFETY.md). Перед перестановкой проводов выключай питание. У всех разрешённых внешних источников должна быть общая земля. Не соединяй между собой два выходных драйвера.

| Соединение | Назначение |
|---|---|
| PA1 → 1 кОм → PA8 | PWM TIM2_CH2 поступает на TIM1_CH1; вход PA8 должен иметь определённый уровень при отключённом источнике |
| 3V3 → край потенциометра около 10 кОм; другой край → GND | Безопасный изменяемый аналоговый источник |
| Движок → 1 кОм → PA0 | Аналоговый вход; проверить реальную распиновку потенциометра |
| PA9 → RX USB-UART; PA10 ← TX USB-UART; GND ↔ GND | Консоль 3,3-вольтового уровня |
| PB12 → кнопка → GND | Управление; внутренний pull-up |
| PA13 / PA14 / GND ↔ SWD | Отладчик остаётся доступным |

Не подключай питание USB-UART к плате, если оно не выбрано единственным источником по схеме питания. Наличие переключателя «3,3 V» на неизвестном адаптере ещё нужно проверить: он может переключать только питание, а не уровень TX.

Если потенциометра нет, подключай PA0 через 1 кОм сначала к GND, затем к 3V3, переставляя провод при выключенном питании. Сделай два настоящих лога и покажи изменение raw-кода. Это полноценная проверка пути «реальный вход → ADC → DMA → CSV», но только на двух уровнях. В интерфейсе не называй её калиброванным вольтметром.

## Контракт CubeMX

Точное создание проекта описано в [L12](labs/12-capstone-integration.md). Здесь целевые параметры для сверки:

- MCU STM32F103C8T6 или проверенный CB-вариант, без предположений о скрытой памяти.
- HSI 8 МГц, PLL выключен; AHB/APB1/APB2 `/1`. Это номинальная частота, не метрологический эталон.
- ADC1: один regular channel PA0/IN0, right alignment, scan выключен, continuous conversion выключен; запуск от TIM3 TRGO; ADC clock 4 МГц. Калибровка до начала сбора.
- DMA1 Channel1: peripheral-to-memory, half-word/half-word, memory increment, circular; массив `uint16_t adc_dma[200]`; half/full callbacks.
- TIM3: PSC=7, ARR=999, Update TRGO. При номинальных 8 МГц это 1000 запусков/с.
- TIM2_CH2: PA1, PWM; PSC=7. Для 100/500/1000 Гц ARR=9999/1999/999 соответственно; 50% задаётся половиной количества ticks периода.
- TIM1_CH1: PA8, rising-edge input capture, PSC=7, ARR=65535. Один tick номинально 1 мкс; алгоритм должен знать свой допустимый диапазон и wrap.
- USART1: PA9/PA10, 115200, 8N1. Если предыдущая лабораторная начиналась с 9600, изменить и firmware, и терминал.
- SYS Debug: Serial Wire; PA13 и PA14 не отдаются приложению.

Источники для независимой сверки: [datasheet и pin functions](https://www.st.com/resource/en/datasheet/stm32f103c8.pdf), [официальный HAL ADC STM32F1](https://github.com/STMicroelectronics/stm32f1xx-hal-driver/blob/master/Inc/stm32f1xx_hal_adc.h), а также локальная версия HAL и RM0008 из [SOURCES](SOURCES.md). Указанные значения относятся к выбранному профилю; перенос их в проект с другим clock tree без пересчёта запрещён.

## Архитектура и владение данными

Путь данных: TIM3 → ADC1 → DMA → завершённая половина → ограниченный mailbox/очередь → обработка → TX-очередь → UART → host CSV.

1. DMA владеет активной половиной массива. CPU не должен считать её неизменной.
2. По завершении половины callback только фиксирует событие и выполняет предусмотренное L08 короткое действие. Стабильная копия или проверяемое владение нужны до длительного вычисления.
3. В основном цикле вычисляются min/max/mean, читается согласованный snapshot capture и готовится одна запись.
4. USART1 имеет одного TX-владельца: в итоговой сборке ответы и CSV проходят через общий dispatcher `uart_console` из L04. Запись остаётся в очереди/pending-slot, пока передатчик занят; прямой второй `HAL_UART_Transmit` запрещён. Передача выполняется с ограниченными ресурсами и ожиданиями. В обработчиках IRQ нет printf, долгих циклов и HAL_Delay.
5. При переполнении выбрана одна политика, например «отклонить новый блок», и растёт счётчик. Нельзя незаметно заменить старые данные новыми.
6. Watchdog обновляется только после проверки прогресса критических задач за соответствующее окно. Для 100-мс ADC-блоков действует отдельная проверка: 300 мс на первый новый валидный обработанный блок после START, затем 500 мс с последнего такого блока. Для нового сеанса сначала останови acquisition и исключи старую публикацию, убери старые mailbox/pending-данные; выбранный сброс producer sequence выполняется до нового baseline snapshot. Непосредственно перед новым запуском зафиксируй baseline и время START, сбрось sample tracking. Повтор START, отклонённый или подтверждённый без перезапуска в RUNNING, не сбрасывает tracking. Deadline проверяется до приёма блока: возраст `>=300`/`>=500` мс уже просрочен, запоздавший блок не отменяет FAULT. Отсутствие свежести даёт FAULT/invalid при живой диагностике. Это не требование ADC-события в каждом 100-мс окне IO/control. Живой SysTick не означает живую обработку ADC. Отсутствие импульсного сигнала само по себе является допустимым состоянием входа.

Массив ADC на 200 отсчётов занимает 400 байт. Отдельно перечисли память mailbox, обеих очередей, строк и стека; проверь map-файл и запас. Не делай динамические выделения внутри потока измерений без ясной необходимости.

## Формат данных версии 1

Перед записями передай явный маркер новой сессии `# session=<id>`, затем строки метаданных с префиксом `#`: версия протокола, build ID, причина reset, номинальный clock, частота ADC, размер блока, источник тестового сигнала. Если напряжение питания измерено, укажи измеренное значение и инструмент; иначе запиши `vdda_mv=unverified`. Служебные ответы тоже начинаются с `#`, но обычный `# status` не создаёт новую сессию и не сбрасывает проверку seq.

Заголовок CSV:

```text
seq,t_ms,n,min,max,mean_x100,freq_mHz,signal_valid,dropped_adc,dropped_tx
```

Смысл полей:

- `seq`: номер обслуженного события завершения ADC-блока. Увеличивается и при отказе mailbox принять блок; пропуск номера виден получателю.
- `t_ms`: временная метка блока по выбранной шкале MCU. В метаданных указать, где она снимается; это не UTC-время.
- `n`: число отсчётов, в штатной конфигурации 100.
- `min`, `max`: крайние raw-коды в блоке.
- `mean_x100`: средний raw-код, умноженный на 100, целое число; например 204850 означает 2048,50.
- `freq_mHz`: оценка частоты в миллигерцах. При `signal_valid=1` значение положительное; при `signal_valid=0` передаётся строго `0`, без старого значения.
- `signal_valid`: `0` при отсутствии свежего периода, недопустимом диапазоне или ошибке capture; старое значение частоты не выдаётся за новое.
- `dropped_adc`: накопленные отказы принятия наблюдаемых ADC-блоков.
- `dropped_tx`: накопленные отказы постановки записи в ограниченную TX-очередь.

Числа в примерах документации являются иллюстрациями формата. Они не считаются результатом аппаратного теста.

`seq` и `dropped_adc` **не могут восстановить точное число DMA-событий**, которые аппаратные флаги потеряли при слишком долгой блокировке IRQ. При обнаруженном нарушении deadline останови сбор и покажи отдельное состояние ошибки. Не продолжай выдавать данные как валидные. Возможность обнаружения такой задержки должна опираться на источник времени, который сам не теряет ход при маскированном SysTick, или быть явно ограничена.

## Скорость и ограничения канала

UART 115200 8N1 передаёт по 10 бит на байт, то есть теоретический предел около 11520 байт/с. При 10 строках/с по 120 байт получается около 1200 байт/с до дополнительной диагностики. Фактическую максимальную длину своей строки всё равно измерь.

Не выводи диагностический текст на каждый ADC-отсчёт. Храни целые числа; float-форматирование не нужно для базового проекта.

Обычный TX/RX без flow control и подтверждений **не сообщает MCU, читает ли компьютер данные**. Остановка Python-программы или выдёргивание USB не обязаны заполнить очередь MCU. Контролируемую перегрузку проверяй искусственной остановкой локального потребителя либо заданным увеличением нагрузки. Доказательство доставки до файла требует проверки самого host-файла; для гарантированной доставки понадобится протокол ACK/повтора и новый проектный контракт.

## Команды и состояния

Минимальный интерфейс:

- `STATUS` возвращает состояние, build ID, частоту сбора, counters и причину последнего reset.
- `START` из допустимого исходного состояния начинает новую сессию по явно описанному правилу сброса seq/counters. Повтор в RUNNING подтверждает текущее состояние либо явно отклоняется; он не сбрасывает counters, baseline или срок свежести.
- `STOP` останавливает новые запуски ADC, завершает или отбрасывает остаток по документированному правилу и остаётся доступным для `STATUS`.
- Кнопка может переключать START/STOP через тот же автомат.

Минимальные состояния: `IDLE`, `RUNNING`, `FAULT`. После питания прибор сначала явно сообщает готовность. После неисправности не запускай бесконечный скрытый цикл «ошибка → reset → ошибка».

Команды изменения частоты или duty можно добавить после устойчивого минимального интерфейса. Каждая новая команда проверяется на длину, диапазон, частичный ввод и недопустимость в текущем состоянии.

## Что сохранить в проекте

- Исходники, `.ioc`, build/debug configuration и README с точными версиями инструментов.
- Pinmap, фактическая схема питания, выбранный clock tree и ограничение входных уровней.
- Команда сборки из свежей копии; firmware build ID, ELF/map и размер секций.
- Протокол версии 1, небольшой исходный CSV и его автоматическая проверка.
- Журнал обычного запуска, перегрузки, потери входного сигнала и watchdog reset.
- Таблица «проверено / не проверено / ограничение» и одна самостоятельная модификация.

Сборка и интеграционная проверка находятся в [L12](labs/12-capstone-integration.md), количественная приёмка и новое требование — в [L13](labs/13-capstone-validation.md). Один исходный CSV с именем build может служить доказательством нескольких проверок; отдельный большой отчёт не нужен. Результаты до изменения принадлежат прежнему build и не переносятся автоматически на новый. Устройство считается продемонстрированным после приёмки, а не после появления первой строки UART.
