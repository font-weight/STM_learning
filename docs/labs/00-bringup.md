# L00. Плата, инструменты и короткая диагностика

**Время:** 1–2 часа практики после установки и загрузок.  
**Результат:** собственный минимальный проект, проверенная запись Flash, остановка в `main` и автономный запуск.  
**Нужно:** Blue Pill с подтверждённым STM32F103C8/CB, SWD-пробник, USB data-кабель, провода, безопасное питание; мультиметр для проверки неизвестного стенда. Внешние модули не нужны.

**Программы для этого маршрута:** CubeMX/STM32CubeF1, VS Code с пакетом ST и **STM32CubeProgrammer с GUI**. Проверьте имеющиеся установки по [TOOLCHAIN](../TOOLCHAIN.md); шаги проверки связи и записи ниже выполняются в GUI CubeProgrammer.

Прочитайте [SAFETY](../SAFETY.md) перед подключением. Если SWD пока нет, можно пройти генерацию и сборку, а затем [UART-ветку](../DEBUGGING.md#uart-bootloader). Отладочные пункты останутся открытыми до появления пробника.

## Короткий мост от Arduino/AVR

| Уже знакомо | В этом проекте | Что важно заметить |
|---|---|---|
| `setup()` | Инициализация в `main` до `while (1)` | Её генерирует CubeMX из `.ioc`; HAL, clocks и GPIO имеют явный порядок |
| `loop()` | Тело `while (1)` | Ваши три строки живут в существующей USER CODE-секции |
| `pinMode` / `digitalWrite` | GPIO init / вызов HAL | Имя вывода — порт и номер; периферии нужны её clock и настройка |
| Upload в Arduino IDE | Build → Flash + verify | Готовый `.elf` ещё не изменяет плату |
| `Serial.print` для поиска ошибки | SWD, breakpoint, Watch | Можно увидеть состояние без добавления UART и остановить сам CPU |

Не нужно учить весь startup-код сейчас. Найдите границу: что готовит генератор, что пишете вы и какой файл получает программатор. Если уже умеете полный STM32-цикл, выполните приёмку ниже и переходите дальше; безопасность и точную цель всё равно проверьте.

## 0. Прогноз до действий, 5 минут

Ответьте без поиска:

1. Какой инструмент превращает C в инструкции Cortex-M3?
2. Почему успешная сборка ещё не означает новую прошивку на плате?
3. Какие две сигнальные линии использует SWD и зачем нужен GND?
4. Если GPIO меняет состояние каждые 500 мс, каков полный период мигания?
5. Что произойдёт после RESET, если BOOT0 оставлен в положении системного загрузчика?

Не нужно угадывать ради балла. Запишите неуверенные ответы: к концу лаборатории вы получите наблюдения, которыми их можно проверить.

## 1. Осмотреть плату и проверить связь, 15–20 минут

1. Запишите маркировку МК и модель пробника. Для C8 оставьте гарантированные 64 КиБ Flash. Отключите внешнюю схему.
2. При снятом питании выставьте штатный запуск из Flash: BOOT0=0. Сверьте подписи перемычек; их физическое положение не универсально.
3. Подключите PA13/SWDIO, PA14/SWCLK, GND и NRST. Подключение питания/VTref выполните по [таблице SWD](../SAFETY.md), а не по цветам проводов.
4. Питайте плату одним выбранным способом и проверьте напряжение.
5. В CubeProgrammer подключитесь по ST-LINK/SWD. Запишите результат идентификации и напряжение. Пока не меняйте Option Bytes и не стирайте память.

**Контрольная точка:** отдельно видны пробник и целевой МК. Если нет, используйте раздел [«МК не отвечает по SWD»](../DEBUGGING.md). Этот этап можно выполнять до написания новой программы.

## 2. Создать минимальный `.ioc`, 15–20 минут

Создайте новый проект в исходном STM32CubeMX через **MCU Selector**, для базового стенда `STM32F103C8T6`. Для подтверждённого CB выберите его точную модель. Blue Pill не требует выбора чужой ST-платы.

| Где | Настройка |
|---|---|
| System Core → SYS | Debug: **Serial Wire** |
| System Core → RCC | HSE: Disable; LSE: Disable |
| Clock Configuration | HSI включён, источник SYSCLK — HSI; PLL выключен |
| Clock Configuration | SYSCLK/HCLK/PCLK1/PCLK2 по 8 МГц; AHB/APB1/APB2 `/1` |
| PC13 | GPIO_Output; Push-Pull; No pull; Low/2 MHz |
| GPIO initial output level | High для проверенного active-low встроенного LED |
| Project Manager | Имя `bluepill_bringup`; Toolchain/IDE: CMake; GCC |
| Code Generator | Keep User Code when re-generating включено |

Сначала проверьте схему своего встроенного LED. Если он не подключён к PC13 подходящим образом, используйте малотоковый внешний LED на PB0 по SAFETY: в настройках и коде замените порт/вывод; начальный уровень для него Low. Это отдельный вариант, не параллельная нагрузка на PC13.

Сохраните `.ioc` и выполните Generate Code. ADC, UART, USB, RTOS и внешние генераторы на этом шаге не включаются. Детальный порядок импорта находится в [TOOLCHAIN](../TOOLCHAIN.md).

**Почему HSI:** сначала проверяется программа и цепочка инструментов без зависимости от неизвестного внешнего кварца. Базовое дерево частот и последующий HSE-вариант находятся [здесь](../TOOLCHAIN.md#clocks).

## 3. Добавить три действия, 10 минут

Откройте сгенерированный `Core/Src/main.c` или соответствующий ему файл в вашей структуре. Найдите существующие пользовательские секции. Не создавайте второй `main` и второй бесконечный цикл.

Внутрь `USER CODE BEGIN PV` поместите счётчик:

```c
static volatile uint32_t blink_edges = 0U;
```

Внутри уже существующего `while (1)`, в его секцию `USER CODE BEGIN 3`, добавьте:

```c
HAL_GPIO_TogglePin(GPIOC, GPIO_PIN_13);
blink_edges++;
HAL_Delay(500U);
```

В варианте внешнего LED замените только вызов GPIO на `HAL_GPIO_TogglePin(GPIOB, GPIO_PIN_0);` и заранее сгенерируйте настройку PB0 вместо PC13.

Прочитайте окружающий `main`: перед циклом должны выполняться `HAL_Init()`, `SystemClock_Config()` и инициализация GPIO. Не переносите весь generated код из чужого проекта, чтобы «сошлись строки».

**Прогноз:** счётчик считает переключения, не полные периоды. Светодиод примерно полсекунды включён и полсекунды выключен. Полный цикл занимает примерно одну секунду; точная частота пока не измерена независимым прибором.

## 4. Собрать, 10–15 минут

1. Откройте корневую папку проекта в VS Code.
2. Выполните обнаружение ST-проекта, выберите GCC и Debug preset, затем Configure и Build согласно [основному маршруту](../TOOLCHAIN.md).
3. Найдите путь к свежему `.elf`; сохраните лог.
4. Посмотрите linker script: C8 — Flash 64K, RAM 20K. Отметьте, где именно сборка сообщает расход памяти.

**Первый маленький успех:** процесс сборки завершился без ошибок и создал новый `.elf`. Сохраните его полный путь: этот же образ нужен для записи и символов отладки. То, что код красиво подсвечен, не является этим критерием. На компьютере без платы на этом можно закончить сегодняшний этап, не объявляя L00 аппаратно пройденной.

## 5. Записать и отличить свою программу, 10 минут

Перед записью убедитесь, что прежняя прошивка платы не нужна. Запись учебного образа заменяет её.

1. Остановите другие debug/programmer-сессии.
2. Запишите свежий `.elf` через CubeProgrammer с verify.
3. Убедитесь в успешной проверке, затем reset/run. Это первый аппаратный успех: программа управляет LED.
4. До изменения предскажите, какими станут интервал между переключениями и полный цикл при `500U → 250U`. Затем соберите, запишите, проверьте и наблюдайте хотя бы 10 циклов. Для грубой оценки можно использовать секундомер: полный цикл должен сократиться примерно с 1 с до 0,5 с. Это не измерение точности HSI.
5. Верните `500U` и повторите полный цикл.

Смена наблюдаемого рисунка доказывает больше, чем постоянно мигающая старая прошивка. Не используйте фотографию неподвижного LED как единственное доказательство.

## 6. Увидеть выполнение в отладчике, 15 минут

1. Отключитесь от target в CubeProgrammer.
2. В VS Code запустите ST debug-сессию с тем же `.elf`. Дождитесь остановки в `main`.
3. Поставьте breakpoint на строку `blink_edges++`. **Предскажите:** первый останов покажет 0 или 1? Выполните Continue и добавьте `blink_edges` в Watch.
4. Для обычной Debug-сборки ожидается такой короткий след: первый останов **до** `++` — 0; Step Over этой строки — 1; следующее Continue до того же места — 1; ещё один Continue — 2. Сопоставляйте подсветку с фактической остановкой: при оптимизации исходная строка может соответствовать нескольким инструкциям. Если след другой, сначала проверьте reset, образ и место breakpoint, а не переписывайте счётчик.
5. Уберите breakpoint и нажмите Continue: свободное мигание должно восстановиться. Не вызывайте функции с побочными эффектами из Watch; здесь достаточно чтения переменной.
6. Завершите debug-сессию, нажмите RESET. Программа должна снова запуститься из Flash без активного debugger.

При остановке CPU мигание не обязано продолжаться. Это ожидаемый эффект эксперимента. Для проверки времени не используйте single-step через `HAL_Delay`.

## 7. Безопасно сломать и восстановить, 10 минут

Выберите **одну** программную ошибку:

- Переименуйте `blink_edges` только в одном месте. Предскажите этап отказа, соберите, найдите первую ошибку и исправьте.
- Соберите изменённую задержку, но намеренно не прошивайте. Объясните, почему поведение платы осталось прежним; затем прошейте и сравните.
- Оставьте CPU на breakpoint. Отличите «программа остановлена» от «прошивка не записалась» и возобновите выполнение.

Не отключайте SWD, не меняйте Option Bytes и не замыкайте выходы ради этой части. Восстановление должно вернуть конкретную рабочую версию, а не просто убрать сообщение об ошибке.

## 8. Приёмка и доказательства

- [ ] Объясняю Generate / Configure / Build / Flash / Debug своими словами
- [ ] Сохранил `.ioc`, исходник, версии и build-лог
- [ ] Подтверждены точная цель и размер памяти
- [ ] Сохранил результат flash verify
- [ ] Получил два разных периода после двух разных записей
- [ ] Остановился в `main` и наблюдал `blink_edges`
- [ ] Восстановил намеренно внесённую программную ошибку
- [ ] После RESET без debugger программа работает

Сохраните в [журнале](../progress-template.md) короткие доказательства; один лог или наблюдение может закрыть несколько пунктов. Рекомендуемые доказательства: лог сборки, лог verify, скриншот остановки/Watch и короткая запись наблюдения после RESET. Серийный номер пробника не обязателен для публичного отчёта.

**Если есть только UART-запись:** не отмечайте debug-пункт выполненным. Генерация/сборка/запись остаются полезным результатом, а наблюдение через SWD — отдельной открытой задачей.

## Проверка переноса

Пользуйтесь документацией и своим журналом действий. В копии рабочего проекта повторите Generate из `.ioc`, убедитесь, что пользовательские строки сохранились, и выполните чистую сборку. Не заменяйте `main` целиком чужим готовым файлом.

Самостоятельно выберите задержку для полного периода около 1,5 с и заранее запишите прогноз. Соберите, прошейте с verify, подтвердите новый период и покажите один останов счётчика. Затем объясните, какие настройки относятся к МК, какие к плате, какие к компьютеру. Содержательную подсказку отмечайте как помощь; окончательный выбор и проверку нового периода выполните сами.

Это проверка решения новой маленькой задачи, а не памяти на меню. На следующий день воспроизведите рабочий Build/Flash/Debug по собственной короткой заметке. Создать второй проект с нуля можно дополнительно, если хочется ещё раз проверить настройку; для этой приёмки повторно щёлкать знакомые меню не требуется.

После уверенного результата переходите к [L01: отладка и GPIO](01-debug-gpio.md) по [маршруту курса](../ROADMAP.md).

## Источники и границы проверки

Настройка и ограничения опираются на [DS5319](../SOURCES.md#s1), [RM0008](../SOURCES.md#s2), [AN2586](../SOURCES.md#s3), [UM1718](../SOURCES.md#s5) и [руководство импорта ST для VS Code](../SOURCES.md#s10). Приведённые пользовательские строки — учебная вставка в сгенерированный HAL-проект, а не самостоятельная готовая прошивка. Физический результат необходимо получить на своём стенде; он не подменяется desktop/static-проверкой материалов.
