# L01. Первый GPIO, регистры и отладчик

Предпосылка: L00 пройден, ST-Link видит МК, питание и SWD проверены. Результат: ты можешь объяснить и проверить весь путь от `Reset_Handler` до изменения напряжения на ножке. Опыт с AVR здесь полезен: меняется организация регистров и тактирования, а не смысл бита.

## Миссия: индикатор, которому можно дать понятное объяснение

Стенд должен показывать короткий импульс «программа выполняется». Другой человек видит LED и спрашивает: «Что именно это доказывает?» Твоя задача — связать исходный код, память, регистры и уровень на выводе, а не просто получить мигание. Исправность всех задач один LED пока не доказывает; к этому вернёмся в L11.

**Маршрут в пределах тех же 3 часов:** новый навык — пройди разобранный путь ниже, затем восстанови пропущенный шаг и выполни самостоятельное изменение в конце. Если GPIO знаком, начни с диагностики и изменения 100/900 ms; пример открывай только там, где не можешь объяснить наблюдение. Адреса памяти, повторная генерация и STM32-регистры всё равно входят в приёмку.

## Что собрать и настроить

Ничего мощного к GPIO не подключать. Штатный LED PC13 с активным нулём используется только если его схема проверена в L00. У неизвестной Blue Pill схема светодиода может отличаться. PC13 не предназначен для питания внешних устройств; его ограничения нужно смотреть отдельно от обычных GPIO. Если в L00 выбран внешний LED, сохрани схему PB0 → резистор 1 kΩ → анод LED, катод → GND. Он активен единицей; ниже этот вариант задаётся один раз через четыре LED-определения, которые используются и в дальнейших лабораторных. Две схемы одновременно для этой работы не нужны.

Продолжай сохранённый рабочий проект L00 или сделай его копию в новую папку. Сохрани подтверждённый точный MCU и выбранный LED; новый проект C8 вместо уже проверенного C8/CB не нужен. В CubeMX проверь:

- `SYS / Debug: Serial Wire`, timebase SysTick, no RTOS
- RCC: HSI включён; HSE, PLL, LSE выключены
- Clock Configuration: SYSCLK = HSI, HCLK = 8 MHz, APB1 = 8 MHz, APB2 = 8 MHz, все делители `/1`
- Выбранный LED: GPIO_Output, push-pull, low speed 2 MHz, no pull; PC13 initial `High`, внешний PB0 initial `Low`
- Для C8 linker script: `FLASH LENGTH = 64K`, `RAM LENGTH = 20K`; для подтверждённого CB сохрани точный chip target из L00, но учебный код по-прежнему укладывай в бюджет 64 KiB/20 KiB

HSI даёт номинальную частоту, а не лабораторный эталон. `SystemCoreClock == 8000000` описывает настройку программы и само по себе не измеряет реальный генератор. Оригинальный CubeMX использует модель GPIO F1 с `CRL/CRH`, не `MODER`, характерный для других серий. [DS5319, память и выводы](https://www.st.com/resource/en/datasheet/stm32f103c8.pdf), [RM0008, RCC и GPIO](https://www.st.com/resource/en/reference_manual/rm0008-stm32f101xx-stm32f102xx-stm32f103xx-stm32f105xx-and-stm32f107xx-advanced-armbased-32bit-mcus-stmicroelectronics.pdf).

## Сначала прогноз, потом запуск

Запиши до прошивки:

1. Какой уровень на выбранном PC13/PB0 включает LED? Что будет до `MX_GPIO_Init()`?
2. Если переключать вывод каждые 250 ms, каков **полный** период сигнала?
3. Зачем выбранному GPIOC/GPIOB нужен собственный clock gate, хотя ядро уже работает?
4. Где лежат код, глобальная инициализированная переменная, нулевая переменная и стек?

## Минимальное приложение

Правила вставки: [интеграция с генератором](../../examples/digital/README.md). Здесь `HAL_Delay` допускается намеренно: это исходная точка для сравнения с L03.

В `USER CODE BEGIN PD` задай вариант своего LED. Ниже готовые значения для проверенного PC13:

```c
#define APP_LED_PORT GPIOC
#define APP_LED_PIN GPIO_PIN_13
#define APP_LED_ON GPIO_PIN_RESET
#define APP_LED_OFF GPIO_PIN_SET
```

Для внешнего PB0 замени четыре значения соответственно на `GPIOB`, `GPIO_PIN_0`, `GPIO_PIN_SET`, `GPIO_PIN_RESET`. Эти определения сохраняются в следующих лабораторных: переключение, постоянный уровень и начальное «выключено» используют один выбранный вариант. [Полная таблица GPIO-замен](../../examples/digital/README.md#led-variants) пригодится для регистрового опыта; настройку CubeMX определения сами не меняют.

`USER CODE BEGIN PV`:

```c
volatile uint32_t probe_data = 0x12345678u;
volatile uint32_t probe_bss;
static uint32_t toggles;
```

`USER CODE BEGIN 0`:

```c
static void led_write(bool on)
{
    HAL_GPIO_WritePin(APP_LED_PORT, APP_LED_PIN,
                      on ? APP_LED_ON : APP_LED_OFF);
}
```

Добавь `#include <stdbool.h>` в `USER CODE BEGIN Includes`. В `USER CODE BEGIN 2`:

```c
volatile uint32_t stack_probe = 0xA55Au;
(void)probe_data; /* observable volatile read: keep the .data object in use */
(void)stack_probe;
led_write(false);
```

Внутри `USER CODE BEGIN 3` **замени прежнее приложение L00** следующим телом цикла. Старые toggle, `blink_edges++` и `HAL_Delay` от L00 не добавляй к новым строкам; иначе два рисунка мигания смешаются. После сохранения результата L00 удали его старый диагностический `blink_edges` из PV: в новой программе он уже не используется.

```c
HAL_GPIO_TogglePin(APP_LED_PORT, APP_LED_PIN);
probe_bss++;
toggles++;
HAL_Delay(250u);
```

Строка `(void)probe_data;` намеренно читает volatile-объект. Без ссылки из выполняемого кода linker garbage collection может удалить даже объявленную volatile-переменную вместе с её секцией. В своём `.map` проверь сохранение `probe_data`; ключевое слово само по себе не заменяет эту проверку. Нативный GCC/ld подтверждает этот механизм, но это не target build STM32.

Сначала собери Debug-конфигурацию с символами и невысокой оптимизацией по инструкции L00. Не начинай с Release: некоторые локальные переменные исчезают после оптимизации, и это не ошибка отладчика.

## Сначала увидеть результат на плате

Собери проект, прошей именно полученный образ с Verify по своему рабочему маршруту L00, затем запусти CPU свободно, без breakpoint внутри цикла. Ожидается мигание: 250 ms включено, 250 ms выключено, около двух полных циклов в секунду. Внешний PB0 и штатный PC13 должны давать одинаковый световой рисунок при разных активных уровнях. Если рисунок не изменился, сначала проверь новый build/Verify, запуск CPU и выбранный GPIO; к исследованию startup переходи после этого короткого наблюдения.

## Разведка startup и памяти, 25 минут

1. Поставь breakpoint в `main` и повтори проверенные в L00 reset/run и остановку. **Дополнительный опыт:** если твоя конфигурация пробника и GDB server документированно поддерживает остановку на startup/reset, попробуй остановиться в `Reset_Handler`. Точная процедура зависит от адаптера и сервера; универсальной команды здесь нет. Если такой режим не настроен, пропусти динамический startup-опыт: обязательный разбор своего startup-файла, linker script и map в следующих пунктах остаётся.
2. Открой **свой** startup-файл. Найди таблицу векторов, копирование `.data` из Flash в RAM, очистку `.bss`, переход к `main`. Порядок дополнительных вызовов зависит от startup/toolchain: объясняй реальный файл, а не рисунок из интернета.
3. В linker script найди Flash с началом `0x08000000`, RAM с началом `0x20000000`, символ вершины стека. При RAM 20 KiB верхняя граница области `0x20005000`; это граница, а не доступный байт SRAM.
4. В `.map` найди `probe_data`, `probe_bss`, секции `.data` и `.bss`. У `.data` есть место загрузки во Flash и рабочий адрес в RAM. Почему ненулевая глобальная переменная расходует обе памяти?
5. Остановись после инициализации `stack_probe`, например перед `led_write(false)`, и посмотри её адрес, значение `0xA55A` и `SP`. Не делай вывод, что стек «имеет постоянный размер»: зарезервированный минимум и худший фактический расход разные вещи.
6. Посмотри первые два слова vector table: стартовый MSP и адрес Reset handler. Младший бит адреса обработчика связан с Thumb state; не исправляй его вручную.
7. Сохрани строку отчёта размера из линкера. `Flash used` и `RAM used` должны быть существенно меньше 64 KiB/20 KiB. Статический отчёт не доказывает отсутствие переполнения стека.

## Тот же GPIO на уровне регистров, 25 минут

После `MX_GPIO_Init()` для PC13 наблюдай `RCC->APB2ENR`, `GPIOC->CRH`, `GPIOC->ODR`, `GPIOC->IDR`. Его четыре бита MODE13/CNF13 находятся в CRH[23:20]. Для PB0 используй GPIOB, CRL[3:0] (MODE0/CNF0), ODR/IDR bit 0 и IOPBEN вместо IOPCEN. По RM0008 расшифруй поля именно своего вывода; не переноси бит 13 в GPIOB автоматически. `ODR` хранит установленное состояние выхода, `IDR` отражает входное считывание ножки. `BSRR` — регистр записи команд, его чтение не заменяет чтение состояния.

Временно замени HAL-переключение на две явные операции, по одной на очередной итерации:

```c
/* Selected pin high: PC13 LED off; external PB0 LED on. */
APP_LED_PORT->BSRR = (uint32_t)APP_LED_PIN;
/* Selected pin low: PC13 LED on; external PB0 LED off. */
APP_LED_PORT->BSRR = (uint32_t)APP_LED_PIN << 16;
```

Не ставь обе строки подряд и не ожидай заметного мигания: между ними нужен интервал. `BSRR` позволяет установить/сбросить выбранные биты одной записью. `GPIOC->ODR ^= ...` является read-modify-write; это важно, если другой контекст меняет тот же порт. Сам факт 32-битного ядра не делает составную операцию атомарной. [RM0008 §9.2, GPIO registers](https://www.st.com/resource/en/reference_manual/rm0008-stm32f101xx-stm32f102xx-stm32f103xx-stm32f105xx-and-stm32f107xx-advanced-armbased-32bit-mcus-stmicroelectronics.pdf).

## Диагностика: программа жива, индикатор не убеждает

**Разобранный шаг для PC13.** После успешного GPIO init запись `BSRR = 1u << 13` задаёт высокий уровень PC13 и выключает active-low LED. Для внешнего PB0 запись `GPIOB->BSRR = 1u` тоже задаёт высокий уровень, но включает LED. Между командой «логическая 1» и смыслом «светится» стоит электрическая схема.

**Восстанови пропущенный шаг, ещё не меняя код.** `probe_bss` растёт, но ожидаемого мигания нет. Две версии: неверная полярность в приложении или отключён clock выбранного GPIO-порта. Назови первое чтение регистра, которое различает эти версии, и ожидаемый результат при каждой. Наблюдение должно проверять причину, а не повторять симптом «темно».

Затем один раз внеси безопасную неисправность: после GPIO init вставь `__HAL_RCC_GPIOC_CLK_DISABLE();` для PC13 или `__HAL_RCC_GPIOB_CLK_DISABLE();` для PB0. Этот опыт относится к L01: после добавления PB12 в L02 отключение GPIOB затронет и кнопку. Сними своё наблюдение, восстанови gate удалением этой строки и повтори ту же проверку. Не отключай SWD и не редактируй option bytes. Если работаешь один, факт внесённой ошибки известен; тренируешь доказательство причины, а не угадывание тайны.

<details>
<summary>Подсказка 1: где разделяются версии</summary>

У обеих версий main может работать. Сначала проверь в `RCC->APB2ENR` разрешение выбранного порта (IOPCEN для PC13, IOPBEN для PB0); лишь после этого трактуй GPIO-регистры. Затем проверь mode выбранного вывода и намеренную запись конкретного уровня. Чтение BSRR не показывает состояние выхода.

</details>

<details>
<summary>Подсказка 2: объяснить и проверить на другом условии</summary>

Отключённый IOPCEN/IOPBEN выбранного порта подтверждает неисправность clock gate. При включённом gate и правильном режиме сравни команду высокого/низкого уровня с `ODR`, `IDR` и реальной полярностью LED. После исправления задай два постоянных состояния отдельно: PC13: высокий выключает, низкий включает; внешний PB0: высокий включает, низкий выключает. Сам рост счётчика не доказывает, что периферия настроена.

</details>

## Измерить и принять

- После 10 секунд без остановок отладчика видно около 20 **полных** циклов; более точную проверку делай логическим анализатором, а не зрением
- У выбранного LED-вывода при паузах состояния близки к 0 V и 3,3 V; мультиметр в режиме DC на мигании может показывать среднее
- Breakpoint внутри цикла меняет измеряемую временную картину. Снимай временные измерения на свободно работающей программе
- В отчёте есть фото/схема, четыре наблюдённых регистра, адреса переменных, размеры Flash/RAM и объяснение полупериода
- Повторная генерация `.ioc` не удаляет пользовательский код; повторная сборка проходит

## Восстановить по памяти

Закрой пример и AI. За 15 минут измени требование: LED включён 100 ms, выключен 900 ms. До запуска нарисуй один полный период с напряжением выбранного LED-вывода и отдельной строкой «LED включён». Затем проверь, что период около 1 s, а включённое состояние занимает около 10%; без прибора раздели расчёт и наблюдение глазом. Покажи в своём startup, откуда взялось начальное значение `probe_data`.

Для отметки «самостоятельно» нужны обе связи: «уровень → свет» и «startup → значение в RAM». Если понадобилась подсказка, это результат «с опорой»: на следующей сессии повтори на 200/800 ms, а не перечитывай весь проект.

Статус материала: код — фрагменты для generated HAL; target build и проверка на плате автором не выполнялись. Критерии выше проверяет учащийся на своём экземпляре.
