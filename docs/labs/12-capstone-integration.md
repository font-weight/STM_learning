# L12 Собрать измеритель из проверенных подсистем

**Результат:** одна прошивка собирает ADC, измеряет частоту, принимает команды и пишет сводки CSV на компьютер.  
**Время:** около 5 часов, четыре сессии по 75 минут.  
**До начала:** пройдены L06, L08, L10 и L11; обязательный SPI из L09 можно завершить отдельно.  
**Контракт прибора:** [CAPSTONE](../CAPSTONE.md).  
**Важно:** это инструкция интеграции, а не заявление о протестированной на физической плате готовой прошивке.

## Инженерная задача

Пять работающих примеров ещё не дают один работающий прибор. Твоя задача — сохранить сбор, измерение, управление и передачу одновременно, а при отказе показать, какой контракт нарушен. Сегодня успех измеряется тем, что новая функция не разрушила уже проверенный путь.

Если такую интеграцию уже делал, начни со своей схемы ресурсов и коротких контрольных точек ниже; пошаговые настройки используй только для сверки. Обязательные аппаратные результаты остаются. Четыре сессии — план на те же 5 часов, а не четыре отчёта.

## Цель и предсказание

До открытия CubeMX запиши:

1. Какова частота появления ADC-блока и сколько времени доступно для его обработки?
2. Кто владеет каждым массивом: DMA, callback, основной цикл или UART?
3. Что произойдёт при занятом mailbox, занятой TX-очереди и исчезнувшем импульсном входе?
4. Какие строки увидит host при `STOP`, `START` и `STATUS`?

Нарисуй пять прямоугольников: сбор, обработка, capture, консоль, передача. Между ними подпиши только данные и ограниченные очереди. Если две подсистемы бесконтрольно изменяют одну структуру, сначала исправь этот контракт.

## Теория на 7 минут

Отдельный пример обычно получает все ресурсы: таймер, callback, буфер, время CPU. В интегрированном приборе это уже общие ресурсы. Надёжность начинается с явного владения и наблюдаемого отказа.

Не объединяй проекты копированием нескольких `main.c` и нескольких сгенерированных IRQ handlers. Создай одну конфигурацию `.ioc`, один набор init-функций и по одной реализации каждого callback. Внутри callback проверяй instance/handle и передавай событие нужной подсистеме.

Один флаг `ready` не является очередью. `volatile` не делает многопольную структуру согласованным snapshot. Ни один вывод UART не должен незаметно изменить частоту аппаратного сбора.

## Сессия 1 Один проект и один источник данных

### CubeMX

Создай новую копию рабочего проекта L08; сохрани её как отдельный проект прибора. Не начинай с чужого `.ioc` для другой платы.

1. Сверь MCU и HSI-профиль: 8 МГц, PLL off, AHB/APB1/APB2 `/1`, ADC `/2`.
2. Сохрани ADC1 PA0, TIM3 TRGO, DMA1 Channel1 circular и IRQ из L08.
3. Добавь TIM2_CH2 на PA1: PWM, PSC=7, ARR=1999, CCR=1000, номинально 500 Гц/50%.
4. Добавь TIM1_CH1 на PA8: rising-edge capture, PSC=7, ARR=65535, нужный IRQ из L06. При отключённом генераторе вход должен иметь определённый уровень; используй проверенную входную конфигурацию L06.
5. Сверь USART1 PA9/PA10: 115200 8N1. Добавь RX IRQ из L04 и механизм TX из L10.
6. Сохрани Serial Wire на PA13/PA14. Кнопка PB12 с pull-up; индикация по проверенной схеме L01.
7. Watchdog пока не запускай: сначала необходимо измерить, что его health-критерии вообще выполнимы. Его настройку добавишь в сессии 4.
8. Сгенерируй и собери. Сверь, что `MX_DMA_Init()` предшествует init ADC, а DMA IRQ вызывает правильный HAL handler.

### Проводка

Выключи питание. Собери PA1→1 кОм→PA8. Добавь аналоговый источник и UART согласно [CAPSTONE](../CAPSTONE.md). Не соединяй неизвестный 5-вольтовый TX адаптера со входом платы. Проверь общую землю и один выбранный источник питания, затем включи.

### Реализация

На этом шаге разрешён только ADC-путь из L08. PWM, capture и команды можно пока не запускать.

- Оставь массив `uint16_t adc_dma[200]` и проверенный mailbox.
- Калибруй ADC до запуска. Сначала запускается DMA/ADC, затем TIM3. Проверь return values.
- Раз в 100 отсчётов вычисляй min/max/mean в основном цикле.
- Сохрани отдельные counters `dma_events`, известных отброшенных блоков и обнаруженных нарушений deadline.
- При `capture_fault` аналоговой подсистемы прекрати сбор и объяви ошибку; это внутреннее имя L08, его не следует путать со статусом частотного входа.

**Контрольная точка:** после старта видно около 10 обслуженных ADC-событий/с, raw-код реагирует на настоящий вход. До включения других функций получи двухминутный чистый лог. Это базовый результат для сравнения.

## Сессия 2 Одна запись и один файл

Введи собственную запись между обработкой и UART. Это пример интерфейса, а не требование конкретных имён:

```c
typedef struct {
    uint32_t seq;
    uint32_t t_ms;
    uint32_t mean_x100;
    uint32_t freq_mHz;
    uint32_t dropped_adc;
    uint32_t dropped_tx;
    uint16_t n;
    uint16_t min;
    uint16_t max;
    uint8_t signal_valid;
} measurement_t;
```

Проверяй фактический `sizeof`, включая padding. Объём очереди считается по реальному размеру структуры.

1. Копируй в запись scalar-результаты, а не указатель на живую половину DMA.
2. `seq` увеличивай для каждого реально обслуженного half/full callback, включая отклонённый mailbox блок. Не перенумеровывай принятые строки так, будто потерь не было.
3. Для `mean_x100` используй проверенную целочисленную арифметику из L10. Для 100 12-битных отсчётов заранее оцени максимальную промежуточную сумму.
4. Формируй ровно десять CSV-полей в порядке из CAPSTONE. Проверь ограничение длины и результат форматирования. Не отправляй строку за пределами её буфера.
5. В итоговом проекте у USART1 один TX-владелец: `uart_console` из L04. Ответы и CSV отправляются из `main` через `uart_console_reply`, которая копирует строку в собственный стабильный буфер. Перед извлечением CSV проверь `uart_console_tx_idle()`. Сначала обслужи ожидающий ответ/метаданные, затем очередную запись. Если отправка не принята, сохрани запись в bounded pending-slot и повтори позже; `HAL_BUSY` сам по себе не означает необходимость выбросить запись. Не запускай параллельный blocking `HAL_UART_Transmit` из L10 и не стартуй передачу из ISR. Если выбираешь другой общий dispatcher, он должен заменить обоих прежних владельцев, а не добавиться третьим.
6. Для смешанного потока добавь префикс `#` ко всем служебным ответам, включая `ERR LINE` в `uart_console.c`. Только строка `# session=<id>` либо новый согласованный CSV-заголовок начинает новую сессию; `# status ...` не сбрасывает проверку последовательности. Метаданные тоже ставятся в общий TX-порядок, а не отправляются несколькими вызовами подряд в занятый передатчик.
7. Сохраняй поток через raw capture терминала, как описано в L10; проверяй сохранённый файл скриптом `tools/check_capture.py`. Отделяй `#`-метаданные/ответы от CSV-строк в соответствии с парсером.
8. Проверь файл после закрытия, а не только бегущий терминал. Укажи имя файла, реальный build ID, число записей и результат проверки seq.

**Контрольная точка:** две минуты лога; `n=100`, `0≤min≤mean_x100/100≤max≤4095`, последовательные seq, нулевые counters в нормальном режиме. Если задержанный callback нельзя безопасно восстановить, файл содержит явное сообщение fault, а не правдоподобные сомнительные данные.

### Разобранный переход: UART уже занят

В момент `t0` общий dispatcher начал передачу ответа STATUS. В `t1` появилась запись ADC, но передатчик ещё занят. Если main извлечёт запись из очереди, попробует отправить и забудет её после `HAL_BUSY`, потеря возникнет в приложении, даже при большом запасе полосы UART.

Рабочий путь: сохранить запись в стабильном ограниченном pending-slot либо оставить её в очереди; дождаться доступности dispatcher; передать ровно один раз. Память нельзя переиспользовать, пока её ещё читает передатчик. В текущем интерфейсе `uart_console_reply` копирует принятую строку; факт принятия всё равно нужно проверить.

**Восстанови пропущенный шаг.** Передатчик освободился, но одновременно ждут метаданные нового сеанса и CSV. Какая запись должна уйти первой и в какой момент можно считать CSV извлечённой? Запиши правило, затем раскрой разбор.

Метаданные новой сессии должны попасть в поток до её CSV. Для одного TX-владельца это вопрос очередности и подтверждения принятия. CSV не исчезает из учёта при неудачной попытке отправки: остаётся в очереди или одном известном pending-slot. ## Сессия 3 Измерение частоты рядом с ADC

1. Добавь проверенные helpers и capture callback из L06. Не создавай вторую функцию с тем же HAL callback-именем.
2. Сначала вооружи capture на PA8, затем запусти PWM на PA1 по порядку из L06.
3. Получай согласованный snapshot периода/валидности. Документируй, как исключено сочетание нового периода и старой временной метки.
4. Преобразуй период в `freq_mHz` с проверкой нуля, диапазона и переполнения промежуточных вычислений. Вычисления не обязаны выполняться в IRQ.
5. Если свежего периода нет дольше установленного timeout, установи `signal_valid=0` и `freq_mHz=0`. Это обязательная пара в протоколе версии 1; старое число частоты не передаётся. При `signal_valid=1` частота должна быть положительной.
6. Проверь 100, 500 и 1000 Гц. Для нового ARR сначала предскажи период; повтори приёмку L06. Помни, что PWM и capture одной платы используют общий источник тактирования.
7. Измени аналоговый вход во время работы capture. Частота и ADC должны сохранять независимый смысл.

**Контрольная точка:** один файл одновременно содержит изменяющийся реальный ADC-вход и правильный статус частоты. Отключение импульсного источника даёт invalid в принятом timeout, а аналоговый сбор продолжается.

Не отсоединяй общую землю в качестве «эксперимента». Для исчезновения сигнала используй остановку PWM с определённым уровнем выхода либо безопасное отключение сигнальной перемычки при выключенном питании.

## Сессия 4 Управление и восстановление

Сделай один автомат `IDLE / RUNNING / FAULT`. И команда, и кнопка должны вызывать один и тот же переход, а не отдельные противоречащие сценарии.

**Сначала расширь парсер L04.** Поставляемый `digital_helpers` понимает LED/PERIOD/PWM/STATUS/STALL; START и STOP в нём пока отсутствуют. Добавь два значения в `digital_command_kind_t`, точные ветки без аргументов в `digital_parse_command` и обработку в автомате. Сохрани строгую грамматику. До прошивки добавь host-тесты: START и STOP принимаются; `START 1`, `STOP extra` и незавершённая строка не исполняются; команда, пришедшая по байту, исполняется только после разделителя; после слишком длинной строки следующая команда работает. `STALL` оставь доступным только в явно включённой тестовой сборке.

1. На старте сообщи build ID и причину reset, затем останься в IDLE до явного START.
2. `START`: сначала проверить допустимое состояние. Для действительно нового сеанса остановить acquisition и исключить публикацию старых данных; затем убрать старые mailbox, ожидающие обработки поколения и записи очередей по выбранной политике. Не переиспользовать память уже принятой UART-передачи до её завершения. Если producer sequence сбрасывается, сделать это **до** нового baseline snapshot. Выполнить calibration, если она требуется выбранным жизненным циклом; непосредственно перед новым сбором зафиксировать свежие baseline sequence и время START, сбросить sample tracking. Затем запустить ADC/DMA до TIM3 и подтвердить переход. Игнорируемый повтор START в RUNNING не вызывает этот сброс tracking и не начинает новый сеанс.
3. `STOP`: сначала остановить TIM3, затем ADC/DMA; обработать или явно отбросить остатки; вернуть управление консоли. Не оставляй строку в очереди указывать на уже переиспользованный буфер.
4. `STATUS`: вернуть состояние, режим, counters, ошибки и reset reason. Неполная или неверная команда не меняет состояние.
5. Добавить health-проверки из L11. В RUNNING требуется прогресс ADC и основного цикла; в IDLE отсутствие ADC-событий является нормой. Не переносить 100-мс bitmap-окно быстрых control-задач на ADC-блоки, которые сами приходят раз в 100 мс: фаза и jitter могут дать ложную ошибку. Для ADC использовать отдельную политику L11: при новом сеансе зафиксировать новый baseline sequence и сбросить sample_seen; дать 300 мс на первый новый валидный обработанный блок, затем 500 мс с последнего принятого прогресса. Возраст `>=300`/`>=500` мс означает истечение соответствующего срока. Сначала проверить deadline, потом принимать блок: уже запоздавший блок не должен молча продлить здоровье или вернуть FAULT в RUNNING. Это отдельный контроль свежести, а 100-мс bitmap остаётся для IO/control. При превышении перейти в FAULT и пометить данные invalid, сохраняя диагностику; IWDG продолжает контролировать продвижение main. Первый запуск таймера ещё не является полученным блоком. Здоровье консоли/передачи определяется её действительными обязанностями, а не обязательным наличием входящих команд. Отсутствие входных импульсов является поддерживаемым `signal_valid=0`, а не поводом бесконечно перезапускать прибор.
6. При смене режима обновить набор health-требований: ожидание ADC разрешено только в RUNNING. Настроить и запустить watchdog по L11. Проверить его отдельно без подключённого отладчика либо с явно зафиксированным поведением debug freeze.
7. Собрать проект из свежей папки по собственному README. Проверить, что ручной код пережил повторную генерацию CubeMX.

**Контрольная точка:** десять циклов START→STOP→STATUS, двадцать нажатий, один намеренный watchdog reset. После восстановления прибор управляем и не выдаёт данные прошлого запуска как новые.

## Локализовать интеграционную неисправность

Выбери одну реальную ошибку интеграции либо один безопасный сценарий ниже. Сначала укажи **две правдоподобные причины и наблюдение, которое их различит**. Порядок действий важнее быстрого угадывания виновного модуля.

| Наблюдение | Первый различающий вопрос |
|---|---|
| ADC-счётчики растут, CSV редеет | Запись теряется до TX-очереди, при отказе dispatcher или уже в host-файле? |
| STATUS пропал после добавления capture | Остановлен main или только испорчен UART-путь? Чем это видно через SWD/счётчик? |
| После STOP→START сразу FAULT | Новая сессия действительно ждёт новый блок или использует старую отметку здоровья? |
| PWM есть, ADC-событий нет | TIM3 запущен и даёт триггеры или проблема дальше по ADC/DMA-пути? |

Для контролируемой проверки можно задержать локального потребителя ADC на 350 мс после выхода в нормальный режим, не запрещая IRQ, либо приостановить локального TX-потребителя. Пользуйся пределами L08/L11; 350 мс сами по себе не обязаны нарушить рабочий deadline 500 мс. Не считай паузу main и длительную маскировку IRQ одинаковым отказом.

После подтверждения причины внеси минимальное исправление, убери injection и повтори тот же сценарий плюс нормальный двухминутный тест. Одного такого расследования достаточно; остальные случаи остаются материалом для возврата, а не дополнительными обязательными часами.

## Приёмка лабораторной

- [ ] Один `.ioc`, один набор IRQ handlers и одна реализация каждого callback
- [ ] ADC, capture, команды и запись работают одновременно
- [ ] Реальный вход изменяет сохранённые raw-данные
- [ ] Ошибки различаются: нет сигнала, известная потеря блока, нарушение deadline, переполнение TX
- [ ] STOP/START воспроизводимы, watchdog не вызывает reset-loop
- [ ] Подсчитаны память и длина строки; сборка из свежей копии проходит
- [ ] Есть реальные короткие логи до и после интеграции и безопасного сбоя

## Восстановить без подсказки

Закрой старую реализацию и чат ИИ. На листе восстанови порядок START/STOP и владельца каждого буфера. Затем напиши заново формирование одной записи из готовых scalar-значений и проверь границы/длину без обращения к старому коду.

## Новый перенос: повтор команды без перезапуска сеанса

Новое требование: оператор может повторить команду, не зная, принял ли прибор предыдущую. В RUNNING повторный START не должен незаметно сбрасывать seq/counters и выдавать старую память за новую сессию; в IDLE повторный STOP не должен запускать сбор. Выбери понятный ответ на такие повторы: подтверждение текущего состояния или явный отказ по состоянию.

Без готового решения сначала опиши ожидаемый результат последовательности `START, START, STATUS, STOP, STOP, STATUS`. Затем измени автомат, если требуется, и проверь тот же сценарий при поступлении команд по символам. Кнопка и UART должны использовать согласованные переходы. Нужны короткий лог и объяснение, какой инвариант ты сохранил, а не ещё один длинный прогон.

Если твоя исходная реализация уже выдерживает это требование и ты проверял такой сценарий, выбери незнакомую перестановку: повтор STOP при ожидающем CSV или START сразу после FAULT с явной политикой восстановления.
