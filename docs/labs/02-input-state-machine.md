# L02. Кнопка, debounce, EXTI и обмен с ISR

Предпосылка: L01. Результат: одно нажатие даёт одно действие; программа различает физические фронты, подтверждённое состояние кнопки и события приложения. Это первая конечная машина курса: вход может шуметь, состояние должно меняться по правилу.

## Миссия: один жест пользователя — одно действие

Кнопка переключает режим стенда. Её можно нажать медленно, удерживать или держать во время включения питания. Твой договор: дребезг и удержание не создают повторных переключений; зажатая при старте кнопка сама не запускает действие. Это выбор поведения устройства, а не настройка NVIC.

В пределах 3 часов сначала восстанови короткую трассу состояний, затем собери один рабочий вариант и объясни одну неисправность. Знакомо: начни с трассы и самостоятельного изменения в конце; исправный polling не освобождает от проверки границы GPIO → EXTI → NVIC.

## Схема и CubeMX

Соедини PB12 с одной стороной нормально разомкнутой кнопки, другую с GND. Включи внутренний Pull-up; для коротких проводов на макетке его достаточно для этого опыта. Не подавай на кнопку внешнее напряжение. У четырёхвыводной тактовой кнопки пары ножек уже соединены внутри: сначала прозвони без питания.

Оставь HSI 8 MHz, SWD, точный MCU и выбранный LED из L01. Сохрани четыре `APP_LED_*` определения; для PB0 они не должны снова стать PC13. Этап A:

- PB12: `GPIO_Input`, Pull-up, метка `BUTTON`
- LED: output push-pull, low speed; PC13 initial high или внешний PB0 initial low согласно [таблице вариантов](../../examples/digital/README.md#led-variants)
- Никаких внешних прерываний пока не нужно

Скопируй helper-файлы по [инструкции](../../examples/digital/README.md). Состояние `pressed` ниже — логическое «нажата», поэтому оно равно `ReadPin == RESET`.

## Этап A. Опрос и подтверждение устойчивого состояния

Параметр `20 ms` — выбранная стартовая настройка лабораторной, не универсальная характеристика всех кнопок. Сначала измеришь свою кнопку, затем обоснуешь значение.

В `USER CODE BEGIN Includes`:

```c
#include <stdbool.h>
#include "digital_helpers.h"
```

После сохранения результатов L01 убери его диагностические `probe_data`, `probe_bss`, `toggles` и строки с `stack_probe`/`(void)probe_data` из приложения. Определения LED, `led_write` и его начальное `led_write(false)` сохрани. Так в новой сборке не остаются неиспользуемые переменные старого опыта.

В `USER CODE BEGIN PV`:

```c
static digital_debounce_t button;
static uint32_t sample_anchor;
static bool led_on;
volatile uint32_t press_count;
volatile uint32_t sample_missed;
```

В `USER CODE BEGIN 2`:

```c
uint32_t now = HAL_GetTick();
digital_debounce_init(&button,
    HAL_GPIO_ReadPin(GPIOB, GPIO_PIN_12) == GPIO_PIN_RESET, now);
sample_anchor = now;
```

Полностью **замени тело приложения L01 внутри `USER CODE BEGIN 3`** кодом ниже. Старые `HAL_GPIO_TogglePin`, `probe_bss++`, `toggles++` и `HAL_Delay` в цикле не оставляй: теперь LED меняется только от подтверждённого нажатия. Инициализацию выключенного LED и его определения сохрани. Просто удалить Delay из старого цикла недостаточно: тогда прежний toggle будет спорить с новым владельцем выхода.

```c
uint32_t now = HAL_GetTick();
uint32_t due = digital_periods_due(now, &sample_anchor, 1u);
if (due != 0u) {
    if (due > 1u) sample_missed += due - 1u;
    bool pressed = HAL_GPIO_ReadPin(GPIOB, GPIO_PIN_12) == GPIO_PIN_RESET;
    digital_button_event_t event =
        digital_debounce_update(&button, pressed, now, 20u);
    if (event == DIGITAL_BUTTON_PRESSED) {
        ++press_count;
        led_on = !led_on;
        HAL_GPIO_WritePin(APP_LED_PORT, APP_LED_PIN,
                         led_on ? APP_LED_ON : APP_LED_OFF);
    }
}
```

`candidate` меняется сразу при новом наблюдаемом уровне; `stable` — только когда этот кандидат сохраняется в выборках не менее заданного интервала. Отдельные устойчивые нажатие и отпускание дают отдельные события. Удержание кнопки не повторяет нажатие. Нажатая при старте кнопка становится начальным состоянием, а не синтетическим событием.

Опрос раз в 1 ms не доказывает, что между выборками не было импульса. Для данной кнопки это осознанное ограничение. Удалённый датчик или точный счётчик импульсов требует другого решения.

## Трасса до платы: что именно подтверждает debounce

В таблице время — входные данные функции на host, не измерение реальной кнопки. Начальное состояние отпущено; порог 20 ms. Первые строки разобраны, остальные заполни до запуска тестов.

| now, ms | pressed | candidate_since после вызова | Событие |
|---:|---|---:|---|
| 1 | true | 1 | NONE |
| 4 | false | 4 | NONE |
| 7 | true | 7 | NONE |
| 26 | true | ? | ? |
| 27 | true | ? | ? |
| 1000 | true | ? | ? |
| 1001 | false | ? | ? |
| 1021 | false | ? | ? |

Какой единственный дополнительный факт даёт строка 27 по сравнению с 26? Сверь прогноз с `test_debounce` в host-тестах.

Это первый обязательный host-запуск: открой [подготовку host-инструментов для своей ОС](../TOOLCHAIN.md#host-tests). Нужны Bash и **native GCC/Clang для компьютера**, не `arm-none-eabi-gcc`. В терминале перейди в корень распакованного курса, где лежат `tests/` и `examples/`, а не в папку CubeMX-проекта, и выполни:

```bash
bash tests/run_digital_tests.sh
```

Для описанного в руководстве Windows/MSYS2 baseline:

```bash
SANITIZE=0 CC=gcc bash tests/run_digital_tests.sh
```

Это пропускает дополнительный sanitizer-прогон, не отмечает его пройденным. Host-инструменты не заменяют firmware toolchain и не меняют настройки прошивки. Затем объясни, почему этот тест не доказывает отсутствие импульсов между реальными выборками.

<details>
<summary>Подсказка 1: от какой отметки считать</summary>

Считай возраст последнего кандидата, а не время с первого фронта и не время с предыдущего вызова. Если `pressed` совпал с кандидатом, его отметка не сдвигается.

</details>

<details>
<summary>Подсказка 2: граница и удержание</summary>

В строках 26 и 27 возраст кандидата равен 19 и 20 ms. Вторая строка меняет `stable` и выдаёт PRESSED; строка 1000 нового перехода не даёт. Отпускание начинает нового кандидата в 1001 и подтверждается в 1021. Условие `>=` включает точную границу; постоянный `pressed=true` не означает повторное событие.

</details>

## Этап B. Сначала ISR, затем главный цикл

Измени PB12 на `GPIO_EXTI12`, режим interrupt on rising **and** falling edge, Pull-up. В NVIC включи `EXTI line[15:10] interrupts`, preemption priority `2`, subpriority `0`; priority grouping — 4 bits preemption, 0 bits subpriority. Оставь SysTick в типичной низкой приоритетности проекта. Меньшее числовое значение NVIC означает более высокий приоритет; прерывание равного приоритета не вытеснит текущее. [PM0056, NVIC](https://www.st.com/resource/en/programming_manual/pm0056-stm32f10xxx20xxx21xxxl1xxxx-cortexm3-programming-manual-stmicroelectronics.pdf).

Проверь после генерации в `stm32f1xx_it.c`:

```c
void EXTI15_10_IRQHandler(void)
{
    HAL_GPIO_EXTI_IRQHandler(GPIO_PIN_12);
}
```

Не копируй второе определение этого handler в `main.c`. Этот вектор общий для линий 10–15: если позже включишь другую линию, обработчик должен обслуживать и её. EXTI12 выбирает один источник порта: PB12 и PA12 нельзя независимо обслуживать как две разные EXTI12 одновременно. [RM0008, AFIO_EXTICR и EXTI](https://www.st.com/resource/en/reference_manual/rm0008-stm32f101xx-stm32f102xx-stm32f103xx-stm32f105xx-and-stm32f107xx-advanced-armbased-32bit-mcus-stmicroelectronics.pdf).

Добавь в `PV`:

```c
static volatile uint32_t edge_pending;
static volatile uint32_t edge_saturated;
volatile uint32_t edges_observed;
```

В `USER CODE BEGIN 4`:

```c
void HAL_GPIO_EXTI_Callback(uint16_t pin)
{
    if (pin == GPIO_PIN_12) {
        if (edge_pending != UINT32_MAX) ++edge_pending;
        else edge_saturated = 1u;
    }
}
```

В `USER CODE BEGIN 0`:

```c
static uint32_t take_edges(void)
{
    uint32_t saved_mask = __get_PRIMASK();
    __disable_irq();
    uint32_t result = edge_pending;
    edge_pending = 0u;
    __set_PRIMASK(saved_mask);
    return result;
}
```

В начале тела `while`: `edges_observed += take_edges();`. Опрос и debounce оставь прежними. Прерывание сообщает о фронтах; решение «считать нажатием» по-прежнему принимает обычный код. Для человеческой кнопки опрос часто проще и достаточен: EXTI здесь нужен, чтобы научиться передавать события и увидеть дребезг.

## Почему volatile недостаточно

`volatile` запрещает компилятору обращаться с общей переменной как с неизменной локальной копией. Он не превращает `++`, `copy; clear;`, проверку с последующей записью или обновление двух полей в одну неделимую операцию.

Без короткой критической секции ISR может увеличить `edge_pending` между копированием и обнулением: новое событие пропадёт. Выравненная 32-битная загрузка/запись на Cortex-M3 и составной алгоритм — разные вещи. Обработчик выше и главный цикл пользуются одним ясным протоколом. Маску восстанавливаем сохранённую, а не безусловно вызываем `__enable_irq()`: иначе вложенный вызов может неожиданно разрешить ранее запрещённые IRQ.

В критической секции только несколько операций с RAM. Не помещай туда ожидание, форматирование, UART send или обработку всех накопившихся событий. Host-тесты проверяют логику, но не доказывают корректность реального межконтекстного доступа.

## Запрещённый учебный антипример

Не исправляй дребезг через `HAL_Delay(20)` в `HAL_GPIO_EXTI_Callback`. При SysTick ниже текущего IRQ время HAL может не продвигаться, и ожидание зависнет. Даже если изменить приоритеты так, чтобы tick проходил, 20 ms внутри ISR блокируют другие задачи. Callback должен быстро записать факт и закончиться. [UM1850, HAL timebase и interrupt API](https://www.st.com/resource/en/user_manual/um1850-description-of-stm32f1-hal-and-lowlayer-drivers-stmicroelectronics.pdf).

## Диагностика без случайной смены всех настроек

Симптом: LED переключается правильно, `press_count` растёт, `edges_observed` остаётся нулём. До проверки выбери между «кнопка не доходит до GPIO» и «не работает interrupt-путь». Назови уже имеющееся наблюдение, которое делает одну версию слабее. Затем проверь этот вывод опытом: временно отключи только NVIC EXTI15_10, повтори нажатие и восстанови настройку.

Два коротких разбора вместо ещё двух перепрошивок:

- При debounce `0 ms` несколько устойчиво считанных фронтов могут стать несколькими действиями. Отсутствие лишних действий на одной кнопке не доказывает, что дребезга не бывает. Повтори физический опыт только если надо проверить собственный порог.
- На бумаге вставь один ISR между `result = edge_pending` и `edge_pending = 0`. При исходном значении 2 покажи, сколько событий попадёт в `result` и сколько исчезнет. После критической секции ни одно событие не должно теряться именно из-за этого interleaving; переполнение счётчика и физические потери — другие вопросы.

Признак хорошего объяснения: ты разделяешь уровень входа, interrupt-событие и подтверждённое действие, а не называешь всё одним «нажатием».

## Измерить и принять

- 20 обычных нажатий → ровно 20 изменений LED; удержание 2 s → одно изменение
- Отпускание на 30 ms и повторное нажатие распознаётся, сверхкороткий импульс менее порога может быть отвергнут
- Логическим анализатором на PB12 измерены дребезг и задержка подтверждения. Без анализатора честно записано, что измерены только программные события
- `edges_observed` показывает сырые фронты, `press_count` — подтверждённые нажатия; их равенство не требуется
- `sample_missed` не растёт в обычной работе без остановок debugger; при breakpoint может расти, что ожидаемо
- Host-команда выше проходит, включая debounce на переполнении `HAL_GetTick`; используемые compiler/ОС и выполненный или пропущенный sanitizer-прогон записаны отдельно

## По памяти и перенос

Без AI и исходного примера нарисуй переходы `stable/candidate`. Новое требование: короткое действие — при подтверждённом отпускании раньше 700 ms; длинное — один раз, когда возраст подтверждённого нажатия достиг 700 ms. После длинного действия отпускание короткого не создаёт. Время удержания отсчитывается от PRESSED после debounce, не от первого сырого фронта.

До реализации запиши ответы для четырёх входных трасс уже подтверждённых событий:

- PRESSED в 100, RELEASED в 799 → одно короткое действие
- PRESSED в 100, проверка времени в 800 → одно длинное; RELEASED в 900 не добавляет короткое
- PRESSED в `0xFFFFFF00`, проверка через 700 ms → одно длинное, несмотря на wrap
- Кнопка зажата при boot → до подтверждённого отпускания и нового PRESSED нет ни короткого, ни длинного действия

Уточни порядок на точной границе: RELEASED в 800 после PRESSED в 100 считается длинным даже без промежуточного вызова. Это проверка правила, а не скорости main. Хватит небольшого host-теста или явной трассы состояний; не требуется в этой же сессии новый интерфейс на плате. Смысл короткого действия изменился относительно переключения на PRESSED: не оставь оба действия одновременно.

Статус: чистая логика проверена host-тестами; IRQ, схема и временные измерения на плате не проверены автором.
