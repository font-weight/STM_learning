# L11: пропавшие и повторные данные после START

Это **host-only задание на самостоятельный перенос**, 25–35 минут в существующем слоте L11. HAL, DMA, UART и IWDG не используются. Успех здесь доказывает переходы чистой логики на заданных трассах; он не заменяет target build, реальные reset-опыты и проверку на плате.

## Задача из жизни стенда

После STOP в памяти остался последний хороший блок. Пользователь нажал START, но новый сбор так и не заработал. Если main продолжает показывать старый результат или отмечает здоровье при каждой отправке старого summary, прибор выглядит исправным.

Напиши маленький `sample_guard`, который проверяет **продвижение обработки новых блоков**. Это не проверка метрологической точности, возраста физической выборки или безопасности DMA-буфера. Передача `validated=true` означает, что вызывающий код уже проверил ownership и корректность блока; функция не может сделать это за него.

## Четыре состояния, один договор

- STOPPED: новые блоки не принимаются; отсутствие данных ожидаемо
- WAIT_FIRST: новый запуск, ждём первый допустимый блок до startup deadline
- LIVE: был принят новый допустимый блок; ждём дальнейший прогресс до stale deadline
- EXPIRED: срок истёк; поздний блок сам не восстанавливает работу

Параметры базового случая — 300 ms на первый блок и 500 ms после последнего принятого. Это **учебная policy для блоков около 100 ms**, не спецификация STM32 или IWDG. Срок истёк при `age >= budget`, поэтому блок ровно на deadline уже опоздал. `accept` сначала проверяет deadline, даже если отдельный `poll` ещё не вызывали.

Вызов `sample_guard_start` означает именно начало нового запуска: он сбрасывает tracking и сохраняет текущий sequence producer как baseline. Повторная идемпотентная команда START в уже работающей сессии должна остаться no-op в dispatcher и не вызывать эту функцию заново. Допустим sequence, продвинувшийся вперёд по модулю 2^32 на 1..2^31−1; повтор, старое значение и неоднозначная разность ровно 2^31 не принимаются. Пропущенные номера возможны: guard проверяет прогресс, а счётчик потерянных блоков ведётся отдельно. Значение ноль после wrap допустимо.

Время в аргументах движется вперёд по модулю, бюджеты лежат в 1..2^31−1 ms. Между сравниваемыми sequence и между обслуживаниями не должно быть неоднозначных расстояний в половину диапазона или более. Из одной отметки нельзя узнать число полных оборотов.

### Порядок START в настоящем приложении

В этом упражнении sequence приходит готовым аргументом. При дальнейшем переносе в L10/L12 порядок важен:

1. Остановить acquisition по протоколу её владельца и исключить публикацию старого запуска
2. Очистить старый mailbox, очереди и ожидающие доставки блоки; при необходимости использовать явный generation identifier
3. Если producer нумерует заново, сначала сбросить его sequence; затем взять согласованный baseline snapshot
4. Запустить guard с этой базой и начать новый поток данных

Если очистка старого поколения не доказана, старый блок с номером 11 может выглядеть новым после сброса producer в 0. Guard по одному числу это не узнает. Не «решай» проблему отключением IRQ надолго или вторым владельцем ADC/DMA.

Отмечай прогресс после проверки и принятия свежего блока из mailbox. Отправка уже накопленного summary из UART-очереди не продвигает ADC. При EXPIRED прикладной слой останавливает обычный поток, помечает ADC-данные недостоверными и переходит в FAULT; живые сервисы диагностики могут кормить IWDG. Поле `signal_valid` итогового CSV относится к частотному входу и для этого не переименовывается.

## 1. Разобранный пример

Это синтетические входы функции, а не запись с платы.

| Событие | Результат | Почему |
|---|---|---|
| START в 1000, baseline 10 | WAIT_FIRST | Старый блок 10 не является первым новым |
| В 1100 принят valid sequence 11 | LIVE, progress=1100 | Новый проверенный блок до deadline |
| В 1599 опять sequence 11 | LIVE, progress всё ещё 1100 | Повтор не обновляет срок |
| В 1600 приходит valid sequence 12 | EXPIRED, блок не принят | Уже прошло ровно 500 ms |
| В 1601 приходит sequence 13 | EXPIRED | Нужен явный новый START |

Назови строку, которая поймает ошибочную реализацию «любое чтение переменной означает прогресс».

## 2. Восстанови пропущенный переход

Не открывая reference, выпиши state и `last_progress_ms` для трассы:

- START в `0xFFFFFF9C`, baseline 100, budgets 300/500
- Через 50 ms приходит valid sequence 101
- Через 200 ms приходит invalid sequence 102
- Через 549 ms после START вызывается poll
- Через 550 ms после START вызывается poll

Затем объясни, почему первое истечение здесь не привязано к возрасту START=300 ms. Если это знакомо, сразу переходи к коду; лишнее переписывание примера не требуется.

<details>
<summary>Подсказка 1: выбери часы текущего состояния</summary>

WAIT_FIRST использует начало запуска и первый бюджет. После принятия нового блока нужны отметка успешной обработки и другой бюджет. Invalid-блок не может передвинуть отметку. STOPPED и EXPIRED не ждут очередного «хорошего» числа.

</details>

<details>
<summary>Подсказка 2: механизм и одна новая проверка</summary>

После первого блока progress равен `0xFFFFFFCE`. Возраст на двух последних строках — 499 и 500 ms; получаются LIVE и EXPIRED. Вычитание выполняется как `uint32_t`; сравнение `now >= anchor + budget` сломает вариант около wrap. Теперь самостоятельно замени baseline на `UINT32_MAX`, а первый sequence на 0: это новый блок, не пустое значение.

</details>

## 3. Допиши scaffold и проверь новую конфигурацию

Редактируй только [student.c](student.c). [sample_guard.h](sample_guard.h) — договор, [test_guard.c](test_guard.c) — открытые критерии. STOP-переход уже заполнен; осталось START, poll и accept. Не нужно менять production `digital_helpers` или добавлять новый UART callback.

Из корня курса:

```bash
bash examples/digital/transfer-guard/run_tests.sh --student
```

Нужны Bash и C11-компилятор GCC или Clang. Исходный scaffold **компилируется, но тесты намеренно падают** с exit 1: это не сломанная поставка курса. В начале выбери один failing case и объясни причину до изменения кода. Скрипт собирает во временную папку; после исправления выполняет обычный прогон и AddressSanitizer/UndefinedBehaviorSanitizer. `SANITIZE=0` оставляет только обычный прогон, `CC=clang` выбирает Clang.

Проверка близкого переноса уже включена в тесты: budgets 180/420 ms. Она показывает, что код переносит смену параметров, но сама по себе не доказывает полностью самостоятельный навык. Реализация с зашитыми 300/500 не пройдёт. Добавь ещё один собственный тест до просмотра reference: например, STOP во время WAIT_FIRST и повторный START с другой базой. Предскажи результат на бумаге.

### Что считается результатом

- **Самостоятельно:** договор объяснён; своя реализация проходит тесты; одна новая трасса придумана и предсказана без AI/готового reference
- **С опорой:** понадобилась подсказка или сравнение с reference; сохрани конкретную причину и повтори изменённую трассу на следующей сессии
- **Нужна доработка:** зелёный запуск reference принят за собственную реализацию или не объяснено, почему повторный блок не продлевает срок

Одного лога тестов и разбора одного важного отказа достаточно. Не оформляй ещё семь отчётов. Если 25–35 минут закончились, сохрани failing case и продолжи с него в следующей сессии; новый аппаратный опыт пока не нужен.

### Reference после своей попытки

[reference.c](reference.c) — одна проверенная реализация того же договора. Она отдельно проверяется командой:

```bash
bash examples/digital/transfer-guard/run_tests.sh --reference
```

Эта команда проверяет материалы курса. Она не выдаёт зачёт собственной работе и не входит вместо аппаратного gate L11. Проверки охватывают границы срока, повторы/старые/invalid-блоки, START после прежнего RUN, stopped-состояние, wrap времени и sequence, новые budgets и атомарный отказ неверной конфигурации.

Снаружи guard остаются реальная атомарность snapshot, очистка старого поколения, принадлежность буфера, задержки main, HAL recovery и физический IWDG. Их проверяют в соответствующих лабораторных, а не этим host-тестом.
